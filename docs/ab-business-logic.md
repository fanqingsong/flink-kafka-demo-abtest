这份文档只讲业务决策：谁看到哪个版本、哪些行为算这个版本的效果、页面上的数字是什么意思。组件怎么连、字段怎么变，见 [数据模型与端到端数据流](data-model-and-flow.md)。SDK 和接口见 [埋点与 A/B 测试 MVP](ab-testing-mvp.md)。

## 1. 这个实验想回答什么

A/B 测试把用户分成几组，每组看到同一个功能的不同做法，再比较各组的点击和购买。差别要能归因到「看到的版本」，而不是碰巧点进来的人本来就更爱买。

本仓库的演示问题是：结算按钮写成「立即购买」还是「马上抢购」，点击和购买有没有差别。

要回答它，系统做四件事：

1. **分流**。决定这个用户看哪个按钮。配置不变时，同一个人每次都看同一个。
2. **曝光**。记录他确实看到了这个按钮。没看到，后面的点击不能算这个版本的。
3. **行为**。记录点击和购买。
4. **归因和汇总**。只把「看到之后、同一版本上、7 天内」的行为算进这个版本，再算点击率和转化率。

## 2. 演示里的人和版本

首次启动会写入实验 `checkout-button`（结算按钮文案）。

| 概念 | 演示里的值 | 业务含义 |
| --- | --- | --- |
| 实验 `experiment` | `checkout-button`，状态 `RUNNING` | 一次对比。只有运行中的实验才分流、才收埋点。 |
| 流量 `traffic_percent` | `100` | 百分之多少的用户进入实验。100 表示谁来都进。 |
| 版本 `variant` | `control` 立即购买，权重 50；`treatment` 马上抢购，权重 50 | 用户实际看到的一种做法。权重是进入实验之后的分配比例。 |
| 版本内容 `payload` | 按钮文案和颜色 | 前端用来渲染，不参与统计。 |
| 用户 `user_id` | 浏览器 `localStorage` 里的匿名 ID | 分流和归因都认这个 ID。点「换一个用户」会换成新人。 |
| 会话 `session_id` | 当前标签页的 `sessionStorage` | 同一次浏览。用来避免同一会话重复报曝光。 |

`control` 是对照，`treatment` 是要试的新文案。统计时两者地位相同，都按自己的曝光和行为算指标。

## 3. 打开页面时发生了什么

演示页是 <http://localhost:8088/ab-demo.html>。按一次完整购买，业务顺序是：

1. SDK 取出或生成 `user_id`，再取出或生成 `session_id`。
2. 用实验键 `checkout-button` 和这个 `user_id` 向服务端要版本。
3. 服务端返回进没进实验、版本键、按钮文案和颜色。
4. 如果进了实验，并且这个会话还没为该实验报过曝光，SDK 自动发一条 `exposure`。
5. 页面按返回的文案和颜色画出按钮。
6. 用户点击按钮后，SDK 再发一条 `click` 和一条 `purchase`。购买金额写在 `properties.amount`，演示里是 `99`。

刷新同一标签页不会再发曝光：会话里已经记过「这个实验曝光过了」。关掉标签页再打开是新会话，会再发一条曝光。这条新曝光会不会计入指标，由第 6 节的 7 天规则决定。

「换一个用户」会清掉 `user_id` 和会话，下一次打开就是另一个人，重新分流、重新曝光。

## 4. 分流：进不进实验，进哪个版本

分流发生在 `POST /api/assignments`，不看用户过去点过什么。输入是实验键和用户 ID，输出在整个实验配置不变时是固定的。

计算用：

```text
SHA-256(experimentKey + ":" + userId + ":" + salt) 的前 8 个字节
→ 映射成 0 到 9999 的桶号
```

`salt` 是实验自己的盐。改盐会让同一个人落到另一个桶，所以盐要和实验一起保持稳定。

两步判断：

1. **进不进实验**。桶号 `< traffic_percent × 100` 才进入。`traffic_percent = 100` 时，0–9999 全部进入。若改成 10，只有 0–999 进入，其余用户拿到 `in_experiment = false`，页面不改按钮，也不上报事件。
2. **进哪个版本**。用 `桶号 % 100` 得到 0–99，再按版本权重从左到右累加。演示里 control 占 0–49，treatment 占 50–99。权重之和必须是 100，否则服务端拒绝这份配置。

因此：流量决定「有多少人参加实验」，权重决定「参加的人里各版本占多少」。同一个人在配置不变时永远落在同一个桶，避免他一会儿看「立即购买」、一会儿看「马上抢购」，把两组效果混在一起。

## 5. 三种事件各自代表什么

标准事件只有三个。

| 事件 | 何时产生 | 业务含义 |
| --- | --- | --- |
| `exposure` | `getVariant` 发现本会话还没报过该实验 | 用户看到了分给他的版本。 |
| `click` | 演示页点击购买按钮 | 用户对这个版本做出了点击。 |
| `purchase` | 紧跟在同一次点击之后 | 用户在这个版本上完成购买。`properties.amount` 是金额。 |

曝光是分母的来源。点击和购买是分子的来源。没有曝光，就不能说「这个版本让他点击了」，因为系统无法证明他看过这个版本。

服务端收下事件前会检查：事件名是这三种之一、实验正在运行、`variant_id` 属于这个实验。通过后写入 Kafka，Web 自己不存事件。同一条事件带一个 UUID `event_id`。Flink 按这个 ID 保留 24 小时，重复上报只留第一条。

## 6. 归因：哪些行为算版本的功劳

归因回答：这条点击或购买，能不能算某一次曝光的结果。

Flink 按 `user_id + experiment_id` 记住**最近一次曝光**的时间和版本。不同实验互不影响。判定窗口是 7 天。

### 曝光自己

| 情况 | `attributed` | 最近曝光 |
| --- | --- | --- |
| 这个用户在这个实验上还没有曝光 | `1` | 更新为这一次 |
| 距离上次曝光不超过 7 天 | `0` | 仍更新为这一次 |
| 距离上次曝光已超过 7 天 | `1` | 更新为这一次 |

`attributed = 1` 的曝光才进入「曝光用户数」。窗口内的再次曝光不重复计人，但会把锚点换成最新的一次，后面的点击改和这次比。

### 点击和购买

四条同时满足才是 `attributed = 1`：

1. 之前有过曝光。
2. 事件上的 `variant_id` 和最近曝光的版本相同。
3. 事件时间不早于那次曝光。
4. 距离那次曝光不超过 7 天。

点击和购买只读取最近曝光，不会改它。

用作业注释里的顺序看一个用户。他先看到版本 A：

| 顺序 | 事件 | 结果 | 原因 |
| --- | --- | --- | --- |
| 1 | 10:00:00 曝光 A | `attributed = 1` | 窗口内第一次看到 A，并记住这次曝光 |
| 2 | 同一 `event_id` 再报一次 | 被去重丢掉 | 24 小时内相同事件只留一条 |
| 3 | 10:00:40 点击 A | `attributed = 1` | 曝光之后、同一版本、7 天内 |
| 4 | 10:00:50 点击 B | `attributed = 0` | 最近曝光是 A，这条是 B |
| 5 | 10:01:10 购买 A，金额 19.9 | `attributed = 1` | 仍落在版本 A 的窗口里 |
| 6 | 若 10:05 又曝光 A | `attributed = 0` | 7 天内不是第一次；锚点改成 10:05 |
| 7 | 10:06 点击 A | `attributed = 1` | 和 10:05 这次曝光比，版本和时间都符合 |

第 4 条会留在事件明细里，但 Dashboard 和分钟指标都不把它算进版本 B。第 6 条也不增加曝光用户数。

演示页同一次点击会连发 click 和 purchase，两条都会带着同一次 `getVariant` 返回的版本，所以正常操作下它们和曝光版本一致。

## 7. 页面上的指标怎么读

有两套数字，粒度不同。

### 实验 Dashboard：按人

<http://localhost:8088/ab-dashboard.html> 读事件明细，只统计 `attributed = 1`，并且按用户去重。每个版本一行：

| 指标 | 算法 |
| --- | --- |
| 曝光用户数 | 有过已归因曝光的用户数 |
| 点击用户数 | 有过已归因点击的用户数 |
| 购买用户数 | 有过已归因购买的用户数 |
| CTR | 点击用户数 / 曝光用户数 |
| 转化率 | 购买用户数 / 曝光用户数 |
| 订单数 | 已归因购买的条数，同一个人买两次算两单 |
| GMV | 这些购买的 `amount` 之和 |

CTR 和转化率的分母都是曝光用户，不是全部进站用户。一个人在窗口里曝光多次，曝光用户数仍是 1。他点了两次，点击用户数仍是 1，但若买了两次，订单数是 2。

比较 control 和 treatment 时，看的是各自的 CTR、转化率和 GMV，而不是谁的曝光人数更多。演示权重是 50/50，人数接近是分流的结果，不是效果。

### 分钟指标：按条

<http://localhost:8088/ab-metrics-1m.html> 读 1 分钟聚合。只有 `attributed = 1` 的事件进入窗口，窗口按事件发生时间切，不按到达 Flink 的时间。一行是某个版本在某一分钟里的：

- `exposures`、`clicks`、`purchases`：这一分钟里的事件条数
- `revenue`：这一分钟里购买金额之和

同一分钟里同一个人的两次已归因点击，这里是 2，Dashboard 的点击用户数是 1。所以分钟表的 `clicks` 不能拿去和 Dashboard 的点击用户数对比。

## 8. 容易混的几条边界

- **没进实验就没有事件**。流量没抽中时，页面不渲染实验按钮，SDK 也不发曝光、点击、购买。
- **曝光按会话发，指标按 7 天人去重**。新会话会再发一条曝光事件；7 天内这条事件的 `attributed` 是 0，曝光用户数不增加。
- **再次曝光不计数，但会移动锚点**。窗口内的新曝光把「最近曝光」换成自己。之后的点击必须对上这次的版本和时间。
- **版本不一致一律不算**。点击带的 `variant_id` 和最近曝光不同，这条点击留在明细里，`attributed = 0`。
- **先点击、后曝光不算**。行为时间早于最近曝光，不能算这次曝光带来的。
- **超过 7 天要重新曝光**。旧曝光不再给新的点击背书。下一次曝光自己会重新变成 `attributed = 1`。
- **暂停实验会停掉新数据**。`PAUSED` 或 `DRAFT` 不再接受分流和埋点。已经写进 Kafka 的历史事件仍在分析库里。
- **换盐或改权重会改变谁看哪个版本**。已经发生的曝光不会被重算。之后的新用户按新配置分流。
